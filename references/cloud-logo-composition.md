# Cloud、Kubernetes Logo 与整图组合

## 核对结果与本轮范围

v0.4 已有集群、节点、GPU、内存显存、数据存储、物理互连和 K8s 控制执行描述。本轮只新增五个专门词条：Cloud 环境、CPU、存储服务、平台 Logo、架构连接线；其他条目复用。Agent 文件保持不变。

## 标识先确定归属，再决定放置

Kubernetes 项目 Logo 标识平台，社区资源图标识别 Pod／Service／Node 等资源类型，CPU/GPU/文件/终端等形体识别设备或内容。它们不是互相替换的符号。标识应附着到它所属的标题、边界、组件或接口，而不是画完之后随机贴在空白处。

Logo 与标题同一视觉量级，采用准确素材，不要求必须占某个百分比；核心研究内容仍是主角。详细图把箭头接到真实接口，折叠概览可连到 Logo＋名称组成的平台端点。多集群、独立面板或同一论文的独立图可按阅读需要重复，不制定“全文件只能一个”或“每个节点都一个”的硬限制。

沿用同一文件的素材版本、默认位置逻辑、字体与视觉尺度；Logo 原有轮廓保持准确。图标家族可以不同，但线条密度、视角和比例应相容。必要时使用已有的合适正式素材版本，与周围配色协调，不能随意扭曲标识追求统一。真实 Logo 无法被生图工具保留时留出位置，后排加入官方 SVG/PNG；没有素材就用短文本占位，不生成近似假标识。

## 连接线和资源对象一起安排

布置对象时同时预留主数据通道、访问端口和外围反馈路线。不要最后在图标间强行穿线。边界与括号说明包含，物理链路说明连通，箭头说明实际方向，细映射线说明对应；具体线型含义按本图定义，附紧凑图例。通过标签而非颜色独自承担语义。

共享存储可以在节点组旁或下方，但位置必须反映范围：节点内本地盘、节点间共享服务、集群外部云服务不能不加说明地混放。云存储可用圆柱、bucket 或盘组作为身份，需要表达对象、分片或访问机制再局部展开；“不全靠 icon”不等于禁用常见存储符号。

## 完整组合 A：云原生 GPU 集群

以下仅为构图候选，不默认用户实际部署。

以云轮廓与短平台名标明外层环境，内部用一个带小型 Kubernetes Logo 的集群边界组织节点。节点按组对齐，每台保留 CPU、主存与 GPU 的同风格小组件；只有焦点节点展开本地 SSD 和数据准备路径。若图不涉及云厂商或网络分区，不添加相关 Logo、VPC 或多可用区。

共享存储画在它实际所属范围，用盘组／文件页束／bucket 与短类型标签表示；访问线接到需要数据的工作负载或节点。物理网络采用简化端点与链路，业务访问采用带方向的路径；两者同时出现时明确区分。保留少量真实焦点连接，折叠其余同类路径，避免所有设备之间全连接。

应用可直接放在节点内的 Pod 边界中；需要研究逻辑与部署同时说明时，上方另给简洁逻辑图，通过显式映射线对应下方实例。上方角色不是新增实体；CPU、GPU、存储不因为色彩或相邻位置而被误认为同一种资源。

## 完整组合 B：性能预测与调度运行在 Kubernetes

若预测器和自定义调度组件实际在集群内运行，把它们保留在集群边界内，并用统一强调方式区别既有组件。任务图、预测结果、候选放置是视觉重点，Kubernetes Logo 仅作标题身份。下方展开节点、CPU/GPU 和所需数据位置。预测调用连预测器，控制交互连接具体 API 或对象接口；不要把 CPU→GPU→存储全部串成同一种执行流程。

只需算法总览时可采用逻辑层、平台层、资源层，但标明这是职责分层；不能借层次布局宣称研究模块位于真实集群外。存储缓存是否驻留、对象是否复制，以及被选方案是否实际执行，均由当前研究内容决定。
